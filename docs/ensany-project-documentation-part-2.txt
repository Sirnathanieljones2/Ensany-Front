1. Admin and Operator Layer Added

Ensany now has an internal operator/admin layer.

This is important because the business is not only a user-facing app. It also needs an internal operations system so the team can manage brokers, review request progress, and intervene when a request needs manual handling.

Backend admin route:

src/routes/adminRoutes.js

Admin service logic:

src/services/adminService.js

Admin validation schemas:

src/schemas/adminSchemas.js

Admin role middleware:

src/middleware/auth.js

The admin API is mounted behind:

- requireAuth
- requireAdmin

This means only authenticated users with role ADMIN can access the internal admin endpoints.

2. Admin API Endpoints

The following admin endpoints now exist:

GET /api/admin/overview

Returns platform-wide operational summary data such as:

- total users
- total brokers
- active brokers
- total requests
- requests grouped by status
- due follow-ups

GET /api/admin/brokers

Returns broker records with filtering and counts.

POST /api/admin/brokers

Creates a broker record.

PATCH /api/admin/brokers/:brokerId

Updates a broker record.

GET /api/admin/requests

Returns removal requests across all users with related user, broker, and recent email event data.

GET /api/admin/requests/:requestId

Returns full request detail for operator review.

PATCH /api/admin/requests/:requestId

Allows an admin to update:

- status
- notes
- failureReason
- nextFollowupAt

POST /api/admin/requests/:requestId/notes

Appends an internal note to a request.

4. Admin Request Management Behavior

The admin layer does more than read data. It can also drive workflow state.

When an admin updates a request status, Ensany now records an operator-side EmailEvent entry with provider set to operator.

This creates an auditable timeline showing that a human operator changed the request state.

The update logic also sets timestamps automatically for major transitions:

- EMAIL_SENT
- FORM_SUBMITTED
- COMPLETED
- REJECTED

This keeps dashboard and case history data consistent.

Admin notes are appended with:

- ISO timestamp
- admin email
- note content

This gives internal notes a basic audit trail.

12. What Improved Strategically

After the work covered in the first documentation file, Ensany improved in four major ways.

First: it gained an internal operating system.

This means the company can now manage brokers and requests in a more deliberate way.

Second: it gained broker playbooks.

This moves the product closer to a defensible workflow database rather than a thin email-sending layer.

Third: it gained a real frontend application structure.

This makes further UI work much easier.

Fourth: it gained better regional product alignment.

Arabic/English switching and RTL support move the product closer to its Middle East identity.

13. Current Limitations After This Phase

Even with these improvements, the product is still not ready to launch publicly as a finished business.

Key remaining gaps:

- no verified sending domain yet
- no live Resend production sending
- no public webhook deployment
- no broker edit UI yet
- no broker delete/archive UI yet
- no full form automation system
- no payment and subscription system
- no forgot-password flow
- no refresh token or secure cookie auth strategy
- no background job queue
- no scheduled follow-up worker
- no external monitoring service yet
- no full automated test suite
- no deployment pipeline

14. Recommended Next Steps

The best next steps now are:

1. Finish the profile and intake flow.
Users should be guided through collecting all personal details needed for broker removals before starting a run.

2. Build broker management beyond create/list.
Add broker edit, status management, richer filters, and eventually archive/retire workflows in the admin UI.

3. Build form-required workflows properly.
Some brokers require a web form instead of email. Ensany needs a first-class operator flow for these cases.

4. Set up the real email delivery path once the domain is ready.
That means verifying the sending domain in Resend, wiring the production webhook, and turning off DISABLE_EMAIL_SEND.

5. Add a scheduled follow-up worker.
Ensany needs automated follow-up logic for requests that do not receive timely responses.

6. Strengthen authentication for production.
Add password reset and move toward HTTP-only cookies or a stronger session strategy.

7. Connect external monitoring and alerting.
The platform now has structured logs, readiness checks, and audit logs. The next production step is sending those signals to a hosted monitoring stack with alerts.

8. Add automated tests.
Priority should go to auth, removals, admin APIs, webhook processing, and critical dashboard flows.

9. Continue frontend refinement.
The structure is now healthier, but the visual system, content depth, and trust cues still need more product-level polish.

10. Prepare deployment architecture.
Document hosting, environment management, worker processes, webhook URLs, and operational runbooks.

After this phase, the system can now:

19. Implementation Update: Verified Multi-Step Signup Flow

The signup flow has been redesigned so profile intake is no longer a loose form inside the dashboard.

The new user onboarding order is:

1. User enters account basics.
2. Ensany sends an email verification code.
3. User verifies the email code.
4. User authorizes Ensany to request data removals on their behalf.
5. User enters the personal details required for broker removals.
6. Ensany creates the actual user account and workspace.

Backend changes:

- Added PendingSignup model.
- Added UserAuthorizationConsent model.
- Added prisma/migrations/20260429000300_signup_flow/migration.sql.
- Added POST /api/auth/signup/start.
- Added POST /api/auth/signup/verify.
- Added POST /api/auth/signup/complete.
- Deprecated the old one-step POST /api/auth/register route so it cannot bypass verification and consent.

Security and business behavior:

- Passwords are hashed while the signup is pending.
- Verification codes expire.
- Verification attempts are limited.
- Final account creation requires a verified signup token.
- Consent is stored with version, consent text, electronic signature, IP address, user agent, and timestamp.
- The account is only created after verification, authorization, and intake are complete.
- Non-production development can show the verification code for local testing, but production does not expose it.

Frontend changes:

- Added /signup route.
- Home page start action now goes to /signup.
- Login and signup are still available from the same auth surface, but signup is now a guided flow.
- The signup UI includes account, verification, authorization, and removal profile steps.
- The dashboard no longer throws the full profile form at the user after account creation.
- The dashboard now shows a compact profile readiness card instead.

Audit coverage added:

- SIGNUP_VERIFICATION_STARTED
- SIGNUP_EMAIL_VERIFIED
- REMOVAL_AUTHORIZATION_ACCEPTED

Verification:
