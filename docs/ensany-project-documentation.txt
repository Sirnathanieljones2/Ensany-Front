Ensany Project Documentation
Last updated: 2026-04-28

1. Product Vision

Ensany is being built as a Middle East-focused competitor to privacy removal services such as Incogni and DeleteMe.

The name "Ensany" means "forget me" in Arabic. The core product goal is to help users remove their personal information from data brokers, people-search databases, lead-generation companies, directories, and other entities that collect or expose personal data.

The long-term vision is to provide:

- User account creation and secure profile management.
- Automated and semi-automated data removal requests.
- Email-based removal workflows.
- Form-based removal workflows.
- Request tracking and proof of activity.
- Dashboard visibility for users.
- Internal operator tools for broker and request management.
- Regional privacy expertise for the Middle East.
- Educational privacy content through a blog and expert columns.

4. Environment Configuration

The app now loads environment variables from .env first.

The old env file name is still supported as a fallback, but .env is the preferred standard.

.env is ignored by git and must never be committed.

.env.example documents the expected variables:

DATABASE_URL
JWT_SECRET
PORT
CLIENT_ORIGIN
APP_URL
EMAIL_FROM
RESEND_API_KEY
RESEND_WEBHOOK_SECRET
DISABLE_EMAIL_SEND

Important development setting:

DISABLE_EMAIL_SEND=true

This prevents the app from sending real emails while testing.

5. Neon Database and SSL

The Neon connection string was updated from:

sslmode=require

to:

sslmode=verify-full

This follows the warning printed by the PostgreSQL driver. The warning explained that future pg versions may treat sslmode=require differently, so sslmode=verify-full preserves the stricter behavior.

6. Security Improvements Implemented

The backend now includes:

- Helmet for safer HTTP headers.
- CORS restricted to CLIENT_ORIGIN.
- Express JSON body size limit.
- Rate limiting.
- Centralized error handling.
- Zod input validation.
- JWT authentication middleware.
- bcrypt password hashing.
- No plaintext password storage.
- .env and env ignored by git.
- Prisma instead of raw SQL, reducing SQL injection risk.

Passwords are stored in the database as passwordHash values.

User-facing API responses do not return password hashes.

7. Authentication System

Authentication files:

- src/services/authService.js
- src/routes/authRoutes.js
- src/middleware/auth.js
- src/schemas/authSchemas.js
- src/middleware/validate.js

Auth endpoints:

POST /api/auth/register
POST /api/auth/login
GET /api/auth/me

Registration creates:

- User
- Profile
- bcrypt password hash
- JWT token

Login:

- Finds user by normalized email.
- Compares submitted password against passwordHash.
- Returns a JWT token and public user object.

JWT tokens are currently stored in browser localStorage by the frontend.

This is acceptable for the prototype stage. For production, HTTP-only secure cookies or a stronger session strategy should be considered.

9. Removal Request Workflow

Core file:

src/services/removalService.js

When a user starts a removal run:

1. The API checks that the user exists.
2. The API checks that the user has a profile.
3. Active brokers are loaded from the database.
4. One RemovalRequest is created per user/broker pair.
5. Duplicate requests are avoided using a unique userId + brokerId constraint.
6. Email-capable brokers are processed through the email service.
7. Form-only brokers are marked as FORM_REQUIRED.
8. Email events are recorded.
9. Dashboard data is updated through database state.

Important statuses:

- QUEUED
- EMAIL_SENT
- FORM_REQUIRED
- FORM_SUBMITTED
- IN_PROGRESS
- COMPLETED
- REJECTED
- FAILED
- NEEDS_USER_INFO

11. Email System

The email system was originally built with Nodemailer and Gmail.

It has now been moved to Resend.

Core file:

src/email/emailService.js

The service now:

- Builds the removal email subject.
- Builds plain text email content.
- Builds HTML email content.
- Adds a tracking pixel.
- Sends email through Resend when enabled.
- Adds Resend tags:
  - category
  - request_id
  - broker_id
- Adds custom headers:
  - X-Ensany-Request-Id
  - X-Ensany-User-Id

If DISABLE_EMAIL_SEND=true, the email is not sent.

This is the expected setting until a real sending domain is purchased and verified.

12. Resend Integration

Resend dependency has been installed.

Nodemailer has been removed.

New environment variables:

RESEND_API_KEY
RESEND_WEBHOOK_SECRET

Important:

Production Resend sending requires a verified domain.

Without a domain, Ensany should keep:

DISABLE_EMAIL_SEND=true

Once a domain is purchased:

1. Add the domain in Resend.
2. Add the DNS records Resend provides.
3. Wait for verification.
4. Set EMAIL_FROM to a verified sender, such as:
   Ensany <privacy@ensany.com>
5. Deploy the API publicly.
6. Add the webhook URL in Resend:
   https://api.yourdomain.com/api/webhooks/resend
7. Set RESEND_WEBHOOK_SECRET.
8. Set DISABLE_EMAIL_SEND=false.

13. Email Tracking

Two tracking systems exist now.

First: internal tracking pixel

Endpoint:

GET /api/tracking/email/open/:token.png

This records an OPENED event when the tracking pixel is loaded.

Second: Resend webhook tracking

Endpoint:

POST /api/webhooks/resend

This receives signed Resend events.

The webhook route is mounted before the JSON parser so it can verify the raw request body.

Resend events currently mapped:

- email.scheduled -> SCHEDULED
- email.sent -> SENT
- email.delivered -> DELIVERED
- email.delivery_delayed -> DELIVERY_DELAYED
- email.opened -> OPENED
- email.clicked -> CLICKED
- email.bounced -> BOUNCED
- email.complained -> COMPLAINED
- email.suppressed -> SUPPRESSED
- email.received -> RECEIVED
- email.failed -> FAILED

Webhook retries are deduplicated using providerEventId.

Webhook smoke test:

scripts/testResendWebhook.js

This script:

1. Finds a removal request.
2. Temporarily assigns a fake Resend email id.
3. Processes a fake email.delivered event.
4. Processes the same event again.
5. Confirms the duplicate event is ignored.
6. Restores the request afterward.
7. Deletes the test email event afterward.

19. Security Notes

Current security foundation is much better than the original prototype, but future production work should add:

- Email verification.
- Forgot/reset password.
- HTTP-only cookie auth or refresh-token strategy.
- Stronger rate limits for auth routes.
- Audit logs.
- Admin role enforcement.
- Request ownership checks everywhere.
- Production logging.
- Error monitoring.
- Secrets manager.
- CSRF strategy if cookie auth is adopted.
- Webhook replay protection window.
- Background job isolation.

21. Current Strategic Product Direction

The short-term product should prove:

- A user can create an account.
- A user can provide personal details.
- Ensany can identify relevant brokers.
- Ensany can create removal requests.
- Ensany can send/track emails.
- Ensany can show progress to the user.
- Ensany can support manual operator intervention for complex cases.

The medium-term product should prove:

- Broker workflows can be standardized.
- Form workflows can be tracked.
- Follow-ups can be automated.
- Users trust the dashboard.
- Operators can manage many users efficiently.

The long-term product moat will come from:

- Regional broker database.
- Broker-specific removal playbooks.
- Middle East privacy knowledge.
- Automation plus human review.
- Proof and tracking.
- Strong brand trust.
- Excellent user experience.
